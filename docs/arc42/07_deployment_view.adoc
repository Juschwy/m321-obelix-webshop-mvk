== Deployment View

This chapter describes the **technical infrastructure** required to run the system and
how software building blocks are mapped onto that infrastructure.

=== Infrastructure Level 1 – Overview

==== Overview Diagram

[plantuml, deployment-level1, svg]
----
@startuml
cloud "BBW-Maas Cluster" {
  node "Ubuntu 24.04 VM" as vm {
    package "Application Services" {
      [Frontend]
      [Backend]
    }
    package "Monitoring & Tracing" {
      [Prometheus]
      [Zipkin]
      [Grafana]
    }
  }
}
[Frontend] --> [Backend] : call via HTTP
[Prometheus] --> [Backend] : scrape metrics
[Backend] --> [Zipkin] : send traces
[Grafana] --> [Prometheus] : read metrics
@enduml
----

==== Motivation

The deployment uses a single VM on the BBW-Maas cluster for simplicity, as this is a test/dev environment for a school project. This approach is mandated by the project requirements, which specify docker-compose and a single VM for orchestration. The environment is ephemeral and may be shut down automatically. The separation of frontend and backend (with three backend services) supports parallel development by a large team and reflects the project’s evolution and requirements for microservices and observability.

==== Quality and/or Performance Features

* Environment Type: Development/Test only; not intended for production.
* Availability: Single point of failure (one VM); no redundancy or failover.
* Resource Constraints: VM size and resources are managed by the MAAS system and cannot be customized by the project team.
* Simplicity: Docker Compose and a single VM minimize operational complexity and setup time, as required by the assignment.
* Observability: Zipkin for distributed tracing/logging, Prometheus for metrics, Grafana for visualization, as mandated by the project.
* CI/CD: Automated build, test, and deployment pipelines via GitHub Actions, with a protected main branch and mandatory PR reviews.

==== Mapping of Building Blocks to Infrastructure

[cols="1,2",options="header"]
|===
|Service Group |Infrastructure Element / Node

|Frontend
|Docker container (Nginx) on Ubuntu VM

|Backend
|Docker containers (obelix-webshop, obelix-basket, obelix-quarry) on Ubuntu VM

|Monitoring & Tracing
|Docker containers (Prometheus, Grafana, Zipkin) on Ubuntu VM
|===

==== CI/CD and Deployment

* All code and documentation are managed in a protected GitHub repository.
* Every commit and PR triggers automated tests and builds.
* The main branch is protected and requires three mandatory reviews per PR.
* Deployment to the BBW-Maas VM is automated via GitHub Actions, using docker-compose as required by the assignment.
* The pipeline can provision the VM via the MAAS API; version updates and redeploys connect via WireGuard + SSH to update images and run `docker compose up -d`.

=== Infrastructure Level 2 – Internal Structure

Level 2 zooms into the Ubuntu 24.04 VM and shows all Docker containers and their detailed connections, including trace and metrics flows.

==== Ubuntu 24.04 VM (Docker Host)

==== Diagram

[plantuml, infra-element1, svg]
----
@startuml
node "Ubuntu 24.04 VM" {
  node "obelix-frontend (Nginx)" as frontend
  node "obelix-webshop (reverse proxy)" as webshop
  node "obelix-basket" as basket
  node "obelix-quarry" as quarry
  node "zipkin" as zipkin
  node "prometheus" as prometheus
  node "grafana" as grafana
}
' External access
user --> frontend : HTTP (port 80)
user --> grafana : HTTP (port 3000)

' App traffic
frontend --> webshop : HTTP (port 8080)
webshop --> basket : HTTP (port 8082)
webshop --> quarry : HTTP (port 8081)

' Monitoring and tracing
prometheus --> webshop : scrape /actuator/prometheus (HTTP, port 8080)
prometheus --> basket : scrape /actuator/prometheus (HTTP, port 8082)
prometheus --> quarry : scrape /actuator/prometheus (HTTP, port 8081)
grafana --> prometheus : read metrics (HTTP, port 9090)
webshop --> zipkin : send traces (HTTP, port 9411)
basket --> zipkin : send traces (HTTP, port 9411)
quarry --> zipkin : send traces (HTTP, port 9411)
@enduml
----

==== Motivation

This VM hosts all Docker containers for the project, providing a simple, reproducible environment for development and testing. It is the central point for all application and monitoring services, as required by the assignment and limited by the available infrastructure.
