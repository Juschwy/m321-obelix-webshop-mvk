== Introduction and Goals

=== Introduction

*Obelix* is a class project in which a web-based system is built to sell and manage “Hinkelsteine” (menhirs).
It consists of:

* a *Customer Web UI* to browse and buy menhirs, and
* an *Admin Web UI* to maintain the menhir catalog via CRUD operations (kept intentionally simple: no authentication, no sessions).

The project is developed collaboratively in a single GitHub repository.
All changes are delivered via pull requests (PRs), the *main* branch is protected, and each PR requires *three mandatory reviews*.

This arc42 documentation describes the architecture decisions and the system structure so that the system can be understood, reviewed, and evolved efficiently by new developers joining the project, architects evaluating the design, and penetration testers assessing the system.

=== Requirements Overview

The following key requirements drive the architecture:

Business requirements::

* Customer Web UI for purchasing menhirs.
* Admin Web UI for managing menhirs with CRUD operations (without authentication/sessions).
* Architecture documentation (arc42) for the target audience (new developers, architects, penetration testers, etc.).
* Integration guide that explains how external developers can use the Obelix API, including sample code.
* Automated tests for every pull request and automated deployment to production.

Technical requirements::

* At least *three microservices*.
* Monitoring and tracing: *Zipkin* as well as *Prometheus + Grafana*.
* OpenAPI 3.x definitions per microservice:
  ** generated *code-first*,
  ** readable (descriptions + examples in the YAML),
  ** the frontend uses an *OpenAPI-generated client only*.
* CI pipeline that builds on every commit/PR and deploys the *main* branch; target platform is *BBW MaaS*.
* Documentation is written in *AsciiDoc* and includes architecture diagrams created with *PlantUML*.

Process / collaboration constraints::

* All work is done via PRs with meaningful reviews (no “LGTM-only” reviews).
* Each team member contributes an individual part to the arc42 documentation and delivers it via a solid PR.

=== Quality Goals

The quality goals below are prioritized because they directly support the assignment constraints
(multi-team collaboration, microservices, monitoring, OpenAPI-first integration, and reliable delivery).

[options="header",cols="1,3,3"]
|===
|Priority |Quality goal |Rationale

|1
|Understandability & maintainability
|The system must be easy to explain, review, and extend for new developers and architects.
Clear microservice boundaries and well-documented APIs reduce onboarding time and prevent architectural drift.

|2
|Testability & CI stability
|Every PR must be verified automatically.
A stable pipeline enables fast feedback, prevents regressions, and supports continuous deployment.

|3
|Observability (monitoring, tracing, logging)
|All microservices must be diagnosable in production via tracing and metrics dashboards to speed up debugging and operations.

|4
|API usability for integrators
|External developers need a clear integration guide and high-quality OpenAPI specifications to enable safe client generation and integration.
|===
