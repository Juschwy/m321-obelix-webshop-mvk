== Context and Scope

This section describes the **system context** of the Obelix application.
It defines the system boundaries and identifies all relevant communication partners.
The goal is to clarify **who interacts with the system and how**, both on a business and a technical level.

=== Business Context

The Obelix application is a web-based system for selling and managing Hinkelsteine.
It is used by customers and administrators and provides domain-specific functionality
related to ordering and managing products.

==== Business Context Overview

[cols="1,2,2",options="header"]
|===
|Communication Partner |Inputs to Obelix |Outputs from Obelix

|Customer
|Product search requests, shopping cart actions, order submissions
|Product data, order confirmations, error messages

|Administrator
|Product management requests (create, update, delete), order management requests
|Updated product data, order status information

|Frontend Application
|HTTP requests for business operations
|Business data as HTTP responses (products, orders, users)
|===

==== Business Context Diagram

[plantuml, business-context, svg]
----
@startuml
actor Customer
actor Administrator
actor Frontend

rectangle "Obelix Application (Backend)" {
}

Customer --> "Obelix Application (Backend)" : Browse products, place orders
Administrator --> "Obelix Application (Backend)" : Manage products and orders
Frontend --> "Obelix Application (Backend)" : Forward user requests
@enduml
----

==== Explanation

* The backend system is treated as a **black box** that encapsulates all business logic.
* Authentication and authorization are required for administrative operations.
* Customers can only access public product and order-related functionality.
* All business interactions are triggered indirectly via the frontend.

=== Technical Context

The technical context describes **how communication with the Obelix system is realized**, including protocols, data formats, and infrastructure components.

==== Technical Context Overview

[cols="1,2,2",options="header"]
|===
|Communication Partner |Channel / Protocol |Data Format

|Web Frontend
|HTTPS / REST API
|JSON

|Database (PostgreSQL)
|JDBC
|Relational data (tables)

|Authentication Layer
|HTTP Authorization Header
|JWT (JSON Web Token)
|===

==== Mapping: Input / Output to Channels

[cols="2,2,2",options="header"]
|===
|Business Interaction |Technical Channel |Protocol / Format

|View products
|Frontend → Backend
|HTTPS / REST / JSON

|Place order
|Frontend → Backend
|HTTPS / REST / JSON

|Manage products
|Frontend → Backend
|HTTPS / REST / JSON
|===

==== Notes

* The backend exposes a **RESTful API** secured via HTTPS.
* Data exchange is done exclusively using **JSON**.
* The backend follows a layered architecture (controller, service, persistence).
* No asynchronous messaging or message queues are used.
