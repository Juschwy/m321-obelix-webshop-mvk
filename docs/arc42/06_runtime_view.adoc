[[section-runtime-view]]
== Runtime View

This chapter describes **runtime behavior and interactions** between the building blocks.
It focuses on **architecturally relevant scenarios** and is intentionally limited
to a small, representative set.

Each scenario explains how building blocks collaborate at runtime.

'''

=== Customer purchases a Hinkelstein

==== Purpose
Core business scenario: Customer browses products and adds items to basket.

==== Trigger
User action in the frontend.

==== Involved Building Blocks
* Frontend (Angular + Nginx)
* obelix-webshop (reverse proxy)
* obelix-quarry
* obelix-basket

==== Runtime Diagram

[plantuml, runtime-purchase, svg]
----
@startuml
actor "Customer" as Customer
participant "Frontend" as FE
participant "webshop" as WS
participant "quarry" as Q
participant "basket" as B

Customer -> FE : View products
FE -> WS : GET /products
WS -> Q : GET /products
Q --> WS : 200 products
WS --> FE : 200 products

Customer -> FE : Add to basket
FE -> WS : POST /basket/items
WS -> B : POST /basket/items
B --> WS : 200 item added
WS --> FE : 200 item added
@enduml
----

=== Frontend Runtime Scenarios
==== Scenario 1: User Adds Menhir to Cart
[plantuml, frontend-scenario-1, svg]
----
@startuml
actor User
participant MenhirCardComponent
participant CartService
participant NavbarComponent

User -> MenhirCardComponent : Click "Add to Cart"
MenhirCardComponent -> CartService : addItem(menhir)
CartService -> CartService : Update signal state
CartService -> CartService : Save to localStorage
CartService -> NavbarComponent : Notify cart update (toSignal)
NavbarComponent -> NavbarComponent : Update badge count
@enduml
----
Steps:

* User clicks "Add to Cart" button on MenhirCardComponent
* Component calls CartService.addItem(menhir)
* CartService updates internal BehaviorSubject with new item
* CartService saves updated cart to localStorage
* NavbarComponent receives update via toSignal and displays new count

==== Scenario 2: Admin Creates New Menhir
[plantuml, frontend-scenario-2, svg]
----
@startuml
actor Admin
participant AdminListComponent
participant CreateMenhirModal
participant AdminService

Admin -> AdminListComponent : Click "Create Menhir"
AdminListComponent -> CreateMenhirModal : Open modal
Admin -> CreateMenhirModal : Fill form
Admin -> CreateMenhirModal : Click Submit
CreateMenhirModal -> AdminService : createMenhir()
AdminService --> CreateMenhirModal : Return menhir
CreateMenhirModal --> AdminListComponent : Emit created event
AdminListComponent -> AdminListComponent : Reload list
@enduml
----
Steps:

* Admin clicks "Create Menhir" button
* AdminListComponent sets showCreateModal$$ signal to true
* Admin fills form (weight, stoneType, decorativeness, description, image)
* Image is converted to Base64 for preview and storage
* AdminService.createMenhir() stores menhir in localStorage
* Modal emits created event, AdminListComponent reloads list

==== Scenario 3: User Views Cart
[plantuml, frontend-scenario-3, svg]
----
@startuml
actor User
participant NavbarComponent
participant Router
participant CartComponent
participant CartService

User -> NavbarComponent : Click cart icon
NavbarComponent -> Router : Navigate to /cart
Router -> CartComponent : Activate route
CartComponent -> CartService : getCartItems()
CartService --> CartComponent : Observable items
CartComponent -> CartComponent : toSignal() + display items
CartComponent -> CartComponent : Compute total
@enduml
----
Steps:

* User clicks cart icon in NavbarComponent
* Angular Router navigates to /cart route
* CartComponent loads and calls CartService.getCartItems()
* Items are converted to signal using toSignal()
* Total is calculated automatically via computed signal

==== Notable Aspects
* Frontend calls only webshop; webshop fans out to domain services.
* Observability: backend services emit traces to Zipkin; metrics exposed via /actuator/prometheus.

=== Observability flows (metrics & tracing)

==== Purpose
Show how metrics are scraped and traces are collected.

==== Involved Building Blocks
* obelix-webshop, obelix-quarry, obelix-basket
* Prometheus, Grafana, Zipkin

==== Runtime Diagram

[plantuml, runtime-observability, svg]
----
@startuml
participant "Prometheus" as P
participant "Grafana" as G
participant "Zipkin" as Z
participant "webshop" as WS
participant "quarry" as Q
participant "basket" as B

P -> WS : GET /actuator/prometheus
P -> Q : GET /actuator/prometheus
P -> B : GET /actuator/prometheus
G -> P : Query metrics
WS -> Z : POST /api/v2/spans
Q -> Z : POST /api/v2/spans
B -> Z : POST /api/v2/spans
@enduml
----

==== Notable Aspects
* Prometheus scrapes HTTP metrics endpoints.
* Zipkin receives spans over HTTP.
